# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — type-checks (`vue-tsc -b`) then builds for production; both steps must pass
- `npm run preview` — serve the production build locally

Type checking is the only automated correctness check — there is no test runner.

## Environment

`VITE_NASA_API_KEY` (see `.env.example`) is read in `src/shared/config/env.ts` and injected into every NASA API request by an axios interceptor in `src/shared/lib/http.ts`. Falls back to NASA's `DEMO_KEY` (heavily rate-limited) if unset, with a console warning.

## Architecture: Clean Architecture + feature-first

Each feature under `src/features/<name>/` is split into three layers:

- **`domain/`** — framework-free TypeScript: entities (plain interfaces), a repository interface, and occasionally a use-case class that wraps the repository with validation (e.g. `apod/domain/get-apod.usecase.ts` rejects dates outside NASA's archive range before hitting the network). Domain code never imports Vue or axios.
- **`infrastructure/`** — concrete repository implementations that call the real NASA APIs via axios and map the wire format (snake_case NASA fields) to the domain entity shape (camelCase). This is the only layer that knows about HTTP.
- **`presentation/`** — Vue-specific: a composable (`use<Feature>.ts`) that instantiates the use case/repository and exposes reactive state (`status: 'idle'|'loading'|'success'|'error'`, plus a `refetch`), and the components/views that consume it.

Swapping a data source (e.g. mocking a repository in a test, or pointing at a different backend) means writing a new `infrastructure/` class against the same `domain/` repository interface — nothing in `presentation/` would need to change. There's no DI container; composables just `new` the concrete repository directly (see `useApod.ts`, `useSolarSystem.ts`, etc.) since this project only ever has one implementation per repository.

`src/shared/` holds cross-feature code with no feature-specific knowledge: `config/` (env), `lib/` (axios instances — `nasaHttp` for `api.nasa.gov`, `nasaImagesHttp` for `images-api.nasa.gov`, `eonetHttp` for `eonet.gsfc.nasa.gov` — plus date helpers), `ui/` (StarField, GlassCard, LoadingOrbit, ErrorState), and `layout/` (AppHeader — nav, mobile menu, language toggle). There is no footer component — the Claude Design handoff (see below) doesn't include one, and none was added back.

Seven features share this structure: `apod`, `solar-system`, `mars-rover`, `neo`, `epic` (Earth imagery), `donki` (space weather), `eonet` (natural events).

## Known API caveats

- **Mars Rover Photos endpoint is currently down.** `api.nasa.gov/mars-photos/*` proxies to a Heroku app (`mars-photos.herokuapp.com`) that returns Heroku's "No such app" page (HTTP 404 with an HTML body, not a JSON error) — this is an outage on NASA's side, not a bug in this codebase, and has been an intermittent/long-running issue with this specific NASA endpoint. `NasaMarsRoverRepository` doesn't special-case this response; it surfaces as a normal fetch failure and the view falls back to `ErrorState` with a retry button, which is the correct behavior if/when the endpoint comes back. Don't "fix" this by hardcoding mock data into the repository — if the endpoint is down when you're testing, that's expected, not a regression.
- **The NASA Image and Video Library search is noisy.** `solar-system/infrastructure/nasa-images-solar-system.repository.ts` queries `images-api.nasa.gov/search?q=<planet name> planet&center=JPL` to get a real photo per planet. Two separate false-positive problems showed up during development and both fixes are load-bearing: (1) exoplanet/mission content whose titles mention a planet name in passing (searching "Mercury" surfaced "Kepler-20e"-style results) — fixed by requiring the planet name in the result title (`isRelevantTitle`) and excluding known exoplanet-system terms; (2) unrelated real-world content sharing a planet's name — "Mars" alone matched hundreds of photos from a "Mars Celebration" festival in Mars, Pennsylvania, because NASA's own metadata tags that event with the keyword "Mars". Restricting the search to `center=JPL` (the NASA center responsible for planetary science) eliminates that entire class of false positive. If planet images ever look wrong again, extend these filters rather than removing them — don't drop `center=JPL` or the title check to "simplify" the query.
- **APOD's valid date range is enforced client-side** (`APOD_EPOCH = '1995-06-16'` through today, in `shared/lib/date.ts` and `apod/domain/get-apod.usecase.ts`) since NASA's API returns a generic error for out-of-range dates rather than a clean 4xx.
- **NeoWs feed is single-day only** (`start_date === end_date`) to keep the radar/list simple — NASA's feed endpoint supports up to a 7-day range if that's ever worth adding.
- **EPIC's "most recent images" shortcut (`/EPIC/api/natural/images`) redirects to a broken URL** (`api.nasa.gov` 302s it to a malformed path that 404s). `NasaEpicRepository` avoids it entirely: it calls `/EPIC/api/natural/available` first to get the real list of dates with imagery, then fetches the last one via `/EPIC/api/natural/date/{date}` — don't switch back to the shortcut endpoint.
- **The Exoplanet Archive (TAP API) cannot be called from a browser at all — no CORS support.** This was tried (a full `exoplanets` feature was built against `exoplanetarchive.ipac.caltech.edu/TAP/sync`) and removed after confirming the server never sends `Access-Control-Allow-Origin` and its OPTIONS preflight fails outright — verified with curl (works fine server-side) vs. the browser (blocked). There is no query-string trick or header that fixes this from a pure client-side SPA; it would require a server-side proxy. Don't re-add this feature without adding a backend — a client-only Vue app cannot reach this API.

## Home page's "seven ways in" count is load-bearing

`t.home.modulesTag` (`'07 MODULES'` / `'07 MÓDULOS'`) and `modulesHeading` hardcode the module count in copy — there's no dynamic count derived from the routes list. If a feature is added or removed, update this string in both `en` and `es` in `translations.ts`, and adjust `HomeView.vue`'s bento grid (currently: one 2×2 "Solar System" card, four 1×1 cards that exactly fill the remaining 3-column grid across two rows, and one full-width "Near-Earth Objects" row).

## Design system

This UI was implemented from a Claude Design handoff (a static HTML/CSS/JS mockup export, `Space Explorer v1.dc.html`) — treat `src/style.css` as the source of truth for tokens rather than introducing new ad hoc colors, and check the handoff before making layout changes to any of the pages it covers (home, APOD, Solar System, Mars Rover, NEO — EPIC/DONKI/EONET were added later, matching the same design language but with no mockup of their own).

- **Background**: `StarField.vue` (canvas: twinkling stars in three hues — white/lavender/aurora — with parallax against pointer movement *and* scroll position, occasional shooting stars) is mounted once in `App.vue` behind every route via `-z-10` and `fixed inset-0`. There's no separate nebula/gradient backdrop layer — the mockup only uses colored gradients inside specific cards (the APOD preview, the Solar System bento card), not as a global wash. Don't add one back; it was tried in an earlier iteration and doesn't match the handoff.
- **Color tokens** are defined in `src/style.css` under `@theme` (Tailwind v4's CSS-first config) — `space-*` (backgrounds), `nebula-*` (primary accent, purple), `aurora-*` (secondary accent, teal — used for Earth/hazard-free markers and eyebrows), `solar-*` (warm accent — used for the Sun, rover "active" isn't this, "surprise me"), `danger-*` (hazard/error red), `star-*` (text on dark backgrounds, light-to-dark). Cards use translucent white overlays (`bg-white/[0.025]`–`bg-white/[0.045]` with `border-white/[0.07]`–`border-white/[0.1]`) rather than a solid surface color — match this pattern (see `GlassCard.vue`) instead of introducing an opaque card background.
- **Fonts**: `font-display` (Space Grotesk, headings/buttons/nav) / `font-sans` (Inter, body) / `font-mono` (JetBrains Mono, all numeric/technical readouts — dates, distances, velocities, stat units, eyebrow labels) are declared in `@theme` and loaded via a Google Fonts `<link>` in `index.html` (no build-time font plugin — this is a Vite SPA, not Next.js, so there's no `next/font` equivalent in play).
- **Motion**: prefer pure CSS animation over JS timers for anything transient (the orbit spin in `OrbitView.vue`, the radar sweep in `NeoRadar.vue`, the hazard pulse via `.animate-hazard-pulse` in `style.css`, the fade transitions using the shared `.fade-enter-active`/`.fade-leave-active` classes declared globally in `App.vue`). The starfield is the one place a `requestAnimationFrame` loop is justified, since it needs per-frame canvas redraws.
- **`@keyframes` referenced from an inline `:style` binding must live in an unscoped `<style>` block.** Vue's `<style scoped>` transform silently renames `@keyframes` (e.g. `orbit-spin` → `orbit-spin-c7d59469`) to avoid cross-component collisions — fine when the animation is applied via a scoped *class* (Vue rewrites both sides consistently), but if a component sets `:style="{ animation: 'orbit-spin ...' }"` dynamically, that string is just data to Vue's compiler and never gets rewritten, so the browser can't find a keyframes rule by that name and the animation silently no-ops (no console error, `getComputedStyle().animationPlayState` still reports `'running'`). This broke `OrbitView.vue`'s planet rotation during the redesign. Rule of thumb: any component that references a `@keyframes` name from inline JS/`:style` must declare that `@keyframes` in a plain (non-scoped) `<style>` block, not `<style scoped>`.
- **Deliberate adaptations from the mockup** (the mockup used placeholder gradients since it had no real data source — these are intentional upgrades, not fidelity gaps): the APOD preview card and detail view show the real fetched image instead of a decorative gradient; the Solar System detail panel shows a real NASA photo instead of a gradient swatch; the "Distance from Sun" stat is computed from the real `distanceFromSunAu` domain value (× 149.6 to get million km) rather than hardcoded; the Mars Rover date filter is labeled "Earth date" (not "SOL") because the real API takes a calendar date, not a Martian sol count, and mislabeling it would be factually wrong even though the mockup's fake data used SOL for flavor.

## Routing

Eight routes, statically imported in `src/router/index.ts`: `/` (home/landing), `/apod`, `/solar-system`, `/mars-rover`, `/near-earth-objects`, `/earth` (EPIC), `/space-weather` (DONKI), `/natural-events` (EONET). `App.vue` wraps `<RouterView>` in a `<Transition name="fade" mode="out-in">` for page-to-page crossfades — **this requires every route component to have a single root element**. `HomeView.vue` originally had two sibling `<section>` root nodes, which silently broke navigation into and out of it (Vue logged "Component inside `<Transition>` renders non-element root node that cannot be animated" and the route rendered nothing until a full page reload). If you add a new route view, wrap its template in one root element. Routes are also intentionally *not* lazy-loaded (`() => import(...)`) — that was tried first and combined with `mode="out-in"` produced the same silent-blank-page failure, so plain static imports are used instead; this app is small enough that the bundle-size tradeoff doesn't matter.

`AppHeader`'s desktop nav row shows all 8 links (`hidden xl:flex`) and only collapses to the hamburger + fullscreen mobile menu below the `xl` breakpoint (1280px) — this was bumped up from `md` when the nav grew past 5 items, since 8-9 nav pills don't fit comfortably at tablet widths. If more routes are added, consider a "more" overflow menu instead of pushing the breakpoint even higher.

## Internationalization: full UI chrome translation, NASA API data stays English-only

`src/shared/i18n/translations.ts` (a `Dictionary` interface + `en`/`es` dictionaries) and `src/shared/i18n/language.ts` (`useLanguage()` — a module-level singleton `ref`, not provide/inject, since this is a small SPA with no SSR) provide an EN/ES toggle in `AppHeader`, defaulting to English and persisted to `localStorage`. It covers every string this codebase authored: nav, headings, buttons, empty/loading/error states, and — notably — the Solar System's planet names/descriptions, since those are our own static data (`planet-facts.data.ts`), not NASA API output.

**What is never translated, and why:** APOD titles/explanations, Mars Rover camera names, NEO asteroid designations, EPIC image captions, DONKI event descriptions, and EONET event titles/categories all come live from NASA's APIs, which have no language parameter and return English-only data. Don't try to translate these — there's no API-side way to do it, and astronomical/scientific designations (e.g. "(2007 RT9)", "M5.3 Solar Flare") aren't meant to be translated anyway. If a new feature pulls live NASA text content, follow this same pattern: translate the UI chrome around it, leave the API payload as-is.
